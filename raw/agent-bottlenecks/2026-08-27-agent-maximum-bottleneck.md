# Agent 当前最大的瓶颈究竟是模型能力、工程基础设施，还是缺少真正适合它的业务场景？

## 一、长链路误差累积——1971 年它叫"框架问题"

Agent 最大的瓶颈不是模型、不是工程、不是场景。

是同一个 70 年没解决的问题。

你描述的那些症状——任务规划不稳定、工具调用出错、长链路误差累积、约束太多退化成工作流——看起来像是 2026 年的新问题。但如果你回头翻 AI 历史，会发现每一个症状在符号主义时代就有名字了。

你说的"长链路误差累积"，在 1971 年有个精确的名字：框架问题（Frame Problem）。

当年 SRI 国际研究中心造了一个叫 Shakey 的机器人，用 STRIPS 算法规划行动。它的问题和今天的 Agent 一模一样：执行一个动作后，世界状态变了，但系统不知道哪些变了、哪些没变。

STRIPS 的解法是"帧公理"——显式声明"执行这个动作后，什么不变"。听起来熟悉吗？你今天写的"工具调用后的状态校验""上下文窗口管理""记忆压缩策略"——本质上全都是帧公理。

70 年了，我们在用不同的技术栈解决同一个问题。而且 70 年了，这个问题的本质没变：随着动作链变长，需要跟踪的"不变项"数量指数级增长，最终不可计算。

这就是为什么 Agent 的 Demo 能跑——短链路，三五个步骤，帧公理的负担还能扛。一到真实业务，链路拉到二十步，状态空间爆炸，误差累积，结果不可复现。不是模型不够聪明，是问题本身在数学上就很难。

## 二、约束太多退化成工作流——1976 年它叫"规则脆性"

你说的"约束过多后，Agent 又可能退化成普通工作流"，在 1976 年也有个名字：规则脆性（Rule Brittleness）。

当年斯坦福大学开发了 MYCIN——一个有 600 条规则的医疗诊断专家系统。每条规则单独看都对，但组合起来会冲突、遗漏边界、遇到训练分布外的输入就崩。

MYCIN 的教训是：规则越多，系统不是越强，而是越脆。因为每加一条规则，就多一个潜在冲突点。你以为在加固，实际在增加脆弱性。

今天的"结构化输出、超时重试、模型路由、沙箱隔离、人工确认"——每一条都是合理的工程约束。但叠在一起，你面对的就是 MYCIN 的困境：约束的边际效益递减，冲突的边际成本递增，最终系统变成了一个需要人维护的工作流，而不是自主的 Agent。

这个困境不是工程能解决的。它是架构层面的根本矛盾：你无法用"加约束"的方式让一个系统同时拥有"自主性"和"可靠性"——这两个目标在结构上是互斥的。

## 三、"Demo 能跑，无法交付"——1966 年它叫"ELIZA 效应"

你说的"偶尔能跑，无法交付"，在 1966 年也有个名字：ELIZA 效应。

当年 MIT 的 Weizenbaum 用 200 行代码写了个叫 ELIZA 的聊天程序——简单的关键词匹配，连他的秘书都信以为真，要求他离开房间以便和程序"私下交流"。

ELIZA 效应的核心不是"程序太聪明"，而是：当系统的输出足够流畅时，人会自动补全"理解"这个环节。你看到的"理解"有一部分是你自己投射的。

今天 Agent 的 Demo 也一样。你在 Demo 里看到 Agent 自主规划、调用工具、生成交付物——流畅、连贯、看起来像在思考。但上了生产线，上下文变长、输入变脏、边缘案例变多，那个"理解"的幻觉就碎了。

更麻烦的是 AI 的"谄媚"：面对不确定的信息，它不问清楚，而是顺着你的方向往下编。你给它一个引导性的上下文，它就沿着那个方向生成——不管对不对，先让你满意。这让 Demo 看起来完美，但交付物里藏着幻觉。

## 四、真正的瓶颈：Agent 不知道自己的边界

三个历史原型指向同一个根因。我用三个字概括：自知、自觉、自止。

**不自知：感知有边界**

当前 AI Agent 还是住在电脑里的。它不知道自己工作的电脑在哪家公司、做什么业务、用户的直属领导是谁。发票开专票还是普票这种问题，用户离开工位去财务小姐姐那里问一嘴就行的事，AI 很难获取。

而 AI 的谄媚又让它甚至不知道要问清楚。它不知道自己不知道——这就是"不自知"。

**不自觉：推理链不可审计**

Agent 做了一个决策，你问它"为什么"，它给你一个看起来合理的解释——但这个解释是事后生成的，不是决策过程的真实记录。

我用 Claude Code 做大型项目时，最关键的操作是审查关键代码逻辑——是真的能跑，还是它在骗我。这不是危言耸听。AI 面对不确定的部分，默认行为不是停下来问你，而是编一个看起来合理的实现。

一个不可审计的决策链，在生产环境中就是不可交付的。老板可以接受 Agent 犯错，但不能接受 Agent 犯错了还说不出为什么。

**不自止：不知道什么时候该停**

这是最核心的。当前 AI 的训练目标是"以完成用户任务为优先"。这意味着：

- 用户说"往左移两米"，AI 直接执行，甚至揣测用户偏好
- 用户问一个知识性问题并给了引导，AI 顺着往下编而不是说"我不确定"
- 遇到边界情况，AI 选择"看起来合理"的路径而非"停下来问人"

一个不知道何时该停下来的系统，你不敢把它放到生产环境里。因为生产环境和 Demo 的最大区别不是输入更复杂，而是犯错的代价更高。

## 五、那怎么办？历史给了一条路

三次困境，三次反叛。1986-1991 年，Brooks 给了一个不同于"加约束"的思路：

"世界自身即是它最好的模型。"

他的 subsumption 架构不追求中央规划器的完美，而是让系统分层运作：低层有完整的感知-行动闭环，可以独立运行；高层只在必要时抑制或重定向低层行动。核心特征是优雅降级——高层失效时，低层照常运转。

翻译成今天的工程语言：不是给 Agent 加更多约束，而是把约束设计成"只在必要时介入"的抑制层。低层 Agent 自主执行，高层只在边界被触碰时抑制。低层出错，降级而非崩溃。

这不是理论——Brooks 用这套架构造了能真正在办公室里导航的机器人，而它的中央规划型前辈 Shakey 连走出一个房间都费劲。

## 六、行动指南：现阶段怎么做

### 1. 先建"自止"机制，再建自主能力

你的 Agent 系统第一个该有的不是"自主规划"，而是"什么时候该停下来问人"。具体做法：

- **置信度阈值**：Agent 对自己输出的每一步标注置信度，低于阈值就暂停问人（MYCIN 50 年前就在做这个）
- **关键节点人工确认**：不是每步都确认，只在"不可逆操作"前确认（发消息、删数据、花钱）
- **超时兜底**：长链路任务设全局超时，超时就回退到人工

### 2. 用分层架构替代中央规划

别试图让一个 Agent 管全局。拆成多层：

| 层 | 职责 | 失效后果 |
| --- | --- | --- |
| 执行层 | 工具调用、代码生成 | 单步失败，可重试 |
| 规划层 | 任务分解、链路编排 | 规划失败，降级到执行层单步 |
| 审查层 | 结果校验、边界判断 | 审查失败，回退到人工 |

每一层独立运作，高层失效时低层不崩。这就是 Brooks 的 subsumption 思路。

### 3. 投资"审查能力"而非"提示词工程"

我日常用 AI 做大型项目开发。千问当画师、智谱当代码工程师、DeepSeek 当极速实习生。我变成了 AI 团队的小领导。

这个角色最重要的能力不是"写好提示词"——是审查关键代码逻辑，判断是真的能跑还是 AI 在编。模型越强，产出越逼真，审查越值钱。

### 4. 接受"Agent 不是法律实体"这个现实

Agent 写错了数据，你无法向它追责。责任永远落在人身上。这意味着：

- 涉及钱的决策，人必须确认
- 涉及对外的输出，人必须审查
- 涉及不可逆操作，人必须批准

这不是"约束太多退化成工作流"，这是法律要求的底线。你绕不开。

## 七、回到你的问题

Agent 当前最大的瓶颈究竟是模型能力、工程基础设施，还是缺少真正适合它的业务场景？

都不是。

最大的瓶颈是：我们造了一个不知道自己边界的系统，然后把它放到了容错率为零的生产环境里。

模型会进化，工程会成熟，场景会出现。但"自知、自觉、自止"——知道自己的边界、理解自己的推理、知道何时该停——这个问题从 1960 年 Bar-Hillel 指出自然语言的歧义性到 2026 年 LLM 的幻觉问题，70 年了，还没解决。

这不是悲观。这恰恰是最值得投入的方向——谁能先解决"自止"问题，谁就先能把 Agent 从 Demo 推到生产。
